# COPYCAT_RESPONSE.md - establishing provenance if Paksh is copied

Purpose: make sure Paksh can *prove* what is its own work and *when* it existed, if a copy ever
appears. This is not a legal opinion and does not start disputes by itself. Decisions to contact
anyone, file a platform report, or involve a lawyer are Sameer's (Redstocks Technology LLP).

Guiding rule: **do not try to hide the website** (anything a browser can load can be copied).
Paksh's defence is an accumulating dataset and analysis a clone cannot reproduce, plus clean
evidence of who made what, and when.

---

## 2. What is publicly observable vs proprietary

| Layer | Public? | Note |
|---|---|---|
| UI and interaction patterns | Yes | Anyone can view and recreate them. Copyright protects the *expression* (code, artwork, text), **not** the idea of a left/centre/right bar |
| Client-side app code (`app.js`) | Yes (compiled, not minified-obfuscated) | Not worth hiding; do not spend effort on it |
| Story text and per-side framing | Yes | Scrapeable in bulk from `/data/*.json` and story pages. Provenance = timestamps + our unique wording |
| Outlets' own headlines/snippets | Yes, but **not Paksh's** | Third-party content; Paksh cites it, does not own it. Do not claim otherwise |
| Source-lean roster, methods, thresholds | Roster: partly (outlet + lean shown). Method/thresholds: **no** | Only outcomes are visible |
| Corpus, history, relationships, backups | **No** | The moat. Keep private and backed up |
| Account data | **No** | Supabase, RLS per user |

## 3. Tripwires already built into the product (cheap to check)

- Story JSON-LD states `author: Paksh`, `copyrightHolder: Redstocks Technology LLP`, and cites its
  source articles (`isBasedOn`). Footer: "© 2026 Paksh · A Redstocks Technology LLP product".
- Distinct, stable identifiers a copier is unlikely to strip everywhere: per-story IDs (`/story/<id>`),
  `og:site_name=Paksh`, OG card filenames (`/static/og/<id>.png`), the exact wording of summaries.
- Search a distinctive sentence from a recent Paksh summary in quotes to find verbatim reuse.
  Paksh's own summaries are model-generated in a fixed house style, so unusually specific phrasing
  in a suspect site can be matched to the dated `_site/data/events/<id>.json` snapshot.

## 4. Evidence to preserve when copying is suspected (do this FIRST, before any contact)

1. **Capture the suspect site** - full-page screenshots (desktop + mobile), with the URL and a
   visible clock/timestamp; save the raw HTML (`curl -sL <url> -o page.html`) and note response
   headers (`curl -sI`). Record the date/time and your timezone.
2. **Archive it** - submit the URLs to https://web.archive.org/save/ and keep the returned links;
   this gives an independent third-party timestamp.
3. **Record the matches** - a table: suspect URL | Paksh URL/file | what matches (text, layout,
   markup, asset name) | date seen. Prefer verbatim text matches and identical asset/file names.
4. **Snapshot Paksh's side** - run `py provenance_manifest.py` (writes `provenance/manifest_<date>.json`:
   git HEAD, first commit, SHA-256 of the core source files, DB row counts and date ranges,
   published-site freshness) and **commit it** so git stamps it. Keep the date-stamped backup in
   `backups/` and copy it somewhere off this machine.
5. **Collect the dated history**:
   - Git: `git log --reverse --format='%H %ad %s' --date=iso` (first commit
     `7b1d08d75b`, 2026-06-01 02:07 +05:30; 505 commits, single author account).
     `git log --follow --format='%H %ad' -- <file>` shows when a specific file first existed.
   - GitHub: repository page, commit list, and "Insights -> Contributors" screenshots.
   - Vercel: the project's deployment list - each deployment is immutable and carries a commit SHA
     and timestamp (project created 2026-05-31; `paksh.news` attached 2026-08-08).
   - Supabase: project "Paksh" created 2026-05-07 (dashboard -> Settings).
   - Domain registrar record for `paksh.news`.
6. **Original publication dates** - each story's `datePublished` in its JSON-LD, the `published_at`
   and `created_at` fields in `_site/data/events/<id>.json`, and the RSS feed (`/rss.xml`) item dates.
7. **Design history** - dated screenshots/exports from the design-reference folder (outside the repo), commits
   touching `static/styles.css` / `static/app.jsx`, and any earlier mockups with file metadata.
8. **Do not** alter, delete or "tidy" anything on Paksh's side while preserving evidence, and do not
   contact the operator or post publicly until Sameer decides how to respond.

## 5. Response ladder (Sameer decides each step; none is automatic)

1. **Assess** - is it verbatim copying of *expression* (code, text, images, layout markup), or only
   a similar *idea* (a lean bar, a "coverage gap" concept)? Ideas and methods are generally not
   protectable; verbatim expression is. Also check whether the copied text is really Paksh's or an
   outlet's headline.
2. **Quiet fix first** - most damage is stopped by making the dataset harder to replicate, not by
   takedowns: keep improving analysis, history and coverage (see the roadmap in
   `PAKSH_PRODUCTION_AND_MOAT_REPORT.md`).
3. **Contact** - a polite, factual note to the site operator citing the specific matches.
4. **Platform reports** - the host of the copy (Vercel, Cloudflare, GitHub, registrar) has abuse or
   copyright processes that use exactly the evidence in section 4.
5. **Counsel** - only with a lawyer, and only with the section 4 pack assembled.

## 6. Routine hygiene (so evidence exists before it is needed)

- Monthly: `py provenance_manifest.py`, commit the file, keep an off-machine copy of the newest DB
  backup (`backups/paksh_backup_*.db`).
- Keep git history intact (no history rewrites of `main`); it is the strongest timestamp Paksh has.
- Keep the copyright/publisher fields (JSON-LD, footer, About/Privacy "Operated by Redstocks
  Technology LLP") accurate. Never add claims of patents, "proprietary AI", or legal threats that
  are not true - misleading claims weaken a real complaint.
